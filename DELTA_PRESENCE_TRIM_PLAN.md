# Delta-of-Deltas Trim Plan: cumulative-drift suppression + scene-presence shrink

Status: proposed, not started. Owner: Michael Yarichuk.

## Origin / problem statement

`take_turn`'s Delta mode (`MutationTools.cs`, `DecideTurnModeAsync` 259-339) already trims
per-NPC fields based on **this turn's** `ctx.AppliedChanges`:

- `ShouldStripUnchangedAppearance` (1166-1167), `ShouldSkipBehavioralSummary` (1185-1186),
  `ShouldStripUnchangedGear` (1144-1145) — all `!ctx.AppliedChanges.Any(...)` gates, scoped to
  the current call only.
- `ChangedNeedsKeys` (1194-1217) — same scoping: a need only survives the trim if some
  `NeedChange` **in this turn's batch** moved it by `>= NeedsChangeSignificanceThreshold`
  (default 2). Confirmed via `find_symbol`.
- `AffectsGearOrStats` (1112-1137) already routes `StatusChange`/`StatusRemove`
  (conditions: feared, prone, etc.) and `ItemTransfer`/`ItemEquip`/`ItemUnequip` through the
  "gear changed" gate unconditionally — so **discrete/mechanical deltas are already always sent
  in full, never threshold-suppressed.** This satisfies the "always-full events for
  discrete/mechanical changes" half of the design goal with no code change. Verified, not
  assumed — confirmed by reading the switch body.
- Scene refetch itself is already gated in Delta mode: `RefreshInvolvedEntitiesAsync`
  (1386-1548) only rebuilds a scene that was auto-added (not explicitly requested via
  `ExtraLocationIds`) when `AffectsLocationDetail`/`AffectsScenePresence` (1257-1267) fired for
  it this turn (the `scenesToFetch = scenesToFetch.Where(...)` block, ~1466-1472).

Two real gaps remain, both confirmed by reading the code rather than assumed:

1. **Cumulative drift is invisible.** `ChangedNeedsKeys` compares only the current turn's
   `NeedChange.Delta`, never a value against what the client last actually saw. Hunger ticking
   by 1.5/turn for 5 turns (net +7.5, well past the significance threshold) never surfaces,
   because no single turn's delta ever reaches 2.0. This is a correctness gap, not just an
   efficiency one — the client's model of that NPC silently diverges from server truth.
2. **Every refetched scene resends every present NPC's full (post-field-trim) entry**, even
   NPCs whose presence and fields are both unchanged since they were last surfaced in that
   scene. `RefreshInvolvedEntitiesAsync` line ~1493-1495 applies `ApplyDeltaTrim` per NPC (field
   trim) but never omits/shrinks an NPC's *entry* in `PresentNPCs` based on cross-turn history —
   membership is rebuilt fresh from `BuildSceneSummaryAsync` every time the scene is fetched at
   all, with no per-entry "already sent, still true" check.

Explicitly **not** a gap (design already correct, verify with a test in Phase 0, don't touch):
narrative flavor text ("cheeks blush", "skittish") must never be generated by the engine.
`take_turn` emits structured facts; the LLM's narration skill (`dnd-narration/SKILL.md`)
produces prose from them. Baking narrative strings into `NpcPresenceSummary`/`TurnResult` would
duplicate that responsibility and couple engine code to narrative style. This plan produces
**more structured signal**, never prose.

## Hard constraint carried into every phase

`TurnResult.KnownCharacterIds` (`TurnModels.cs`, computed property at the bottom of the class)
is unioned from `Npcs`, `Party`/`PartyDelta`, and `Scenes[].PresentNPCs` — it's the
do-not-hallucinate ground truth the LLM checks before narrating anyone. **No phase below may
ever remove an NPC's entry from `PresentNPCs` to save bytes.** An unchanged NPC's entry may
shrink to id+name+roster-flags, but it must still appear, or a present character silently drops
out of the known-entities list and the hallucination guard weakens.

## Phase 1 — Cumulative-drift threshold cache for `KnownNeeds`

Closes gap 1. Self-contained; touches `TurnCursor.cs` and `MutationTools.cs` only.

**Current shape** (`TurnCursor.cs` 9-78) already has two "don't re-cost tokens for a stable
reading" caches using the same pattern this needs:
`SurfacedMemoryHintTopicsByEntityId` (`Dictionary<string,string>`) and
`SurfacedCompressedMemoryTopicsByEntityId` (`Dictionary<string,List<string>>`), each written
inline where the value is computed (`MutationTools.cs:989`, `:1035`) via
`ctx.Cursor.<dict>[id] = ...`.

**Add to `TurnCursor.cs`** (after `SurfacedCompressedMemoryTopicsByEntityId`, ~line 78, before
the closing brace):

```csharp
/// <summary>Last need value actually surfaced to the client per entity ID, per need key —
/// the baseline cumulative-drift is measured against, not this turn's NeedChange alone. A need
/// clears the significance bar (CampaignConfig.NeedsChangeSignificanceThreshold) when its live
/// value has drifted far enough from THIS baseline, even if no single turn's delta was enough
/// on its own. Populated for every need on a Full reseed (see DecideTurnModeAsync ~300) and
/// updated only for needs actually included in a Delta response, so an omitted need keeps
/// accumulating against its last-sent baseline.</summary>
[JsonPropertyName("surfacedNeedValuesByEntityId")]
public Dictionary<string, Dictionary<string, float>> SurfacedNeedValuesByEntityId { get; set; }
    = new(StringComparer.OrdinalIgnoreCase);
```

**Modify `ChangedNeedsKeys`** (`MutationTools.cs` 1194-1217). Current signature is `static
IReadOnlyCollection<string>? ChangedNeedsKeys(TurnContext ctx, string characterId)` and it only
sees `ctx.AppliedChanges`. It needs the NPC's *live* `KnownNeeds` to compare against the cursor
baseline, so the call site changes too.

Current call site (`BuildTrim`, 1219-1223):
```csharp
NeedsKeysToInclude: ChangedNeedsKeys(ctx, characterId));
```
`BuildTrim` is called from two places: `ApplyDeltaTrim` (1345, has `npc.KnownNeeds` in scope)
and `RefreshInvolvedEntitiesAsync` (~1531, `BuildTrim(ctx, charId)` — **no live NPC object in
scope at that call site**, since `BuildNpcSummaryAsync` builds the summary *from* the trim, not
the other way around). This means `ChangedNeedsKeys` can't take the live dict as a parameter
without restructuring that second call site.

Resolve by querying the live needs value the same way `BuildNpcSummaryAsync` does (it already
must read `Character.KnownNeeds`/needs storage before applying a trim) rather than passing the
whole NPC in — i.e. `ChangedNeedsKeys` becomes instance (not static), takes `ctx` and
`characterId` as it already does, and internally loads the current need values via whatever
repository call `BuildNpcSummaryAsync` uses for `KnownNeeds` (confirm exact source with
`find_referencing_symbols` on `NpcPresenceSummary.KnownNeeds` before writing — do not assume,
this file listed `Character_Search`/`CampaignRepository.GetPresentNpcsAsync` as the read path
for presence but `BuildNpcSummaryAsync`'s own needs source hasn't been read in this session).

New logic:
```csharp
private IReadOnlyCollection<string>? ChangedNeedsKeys(TurnContext ctx, string characterId, IReadOnlyDictionary<string, float> liveNeeds)
{
    if (ctx.Mode != TurnMode.Delta)
    {
        return null;
    }

    var threshold = ctx.Config?.NeedsChangeSignificanceThreshold ?? 2f;
    var baseline = ctx.Cursor.SurfacedNeedValuesByEntityId.TryGetValue(characterId, out var byNeed)
        ? byNeed
        : new Dictionary<string, float>(StringComparer.OrdinalIgnoreCase);

    var movers = liveNeeds
        .Select(kv => (Need: kv.Key, Value: kv.Value,
            Drift: Math.Abs(kv.Value - (baseline.TryGetValue(kv.Key, out var b) ? b : kv.Value))))
        .Where(x => x.Drift >= threshold)
        .OrderByDescending(x => x.Drift)
        .ToList();

    if (ctx.Request?.LeanMode == true)
    {
        movers = movers.Take(2).ToList();
    }

    if (!ctx.Cursor.SurfacedNeedValuesByEntityId.TryGetValue(characterId, out var toUpdate))
    {
        toUpdate = new Dictionary<string, float>(StringComparer.OrdinalIgnoreCase);
        ctx.Cursor.SurfacedNeedValuesByEntityId[characterId] = toUpdate;
    }
    foreach (var m in movers)
    {
        toUpdate[m.Need] = m.Value;
    }

    return movers.Select(x => x.Need).ToList();
}
```

Note the baseline-miss default (`baseline.TryGetValue(...) ? b : kv.Value`, i.e. "no baseline
recorded yet ⇒ treat as no drift, don't include") — this matters for needs that appear mid
campaign (new need key never seen before): without a recorded baseline they should NOT force an
inclusion purely because the dictionary lookup failed; they piggyback on the very next
`NeedChange` the same way today's per-turn logic already would, avoiding a burst of
false-positive "changed" needs on the delta turn right after a Full reseed introduces a new key.
Confirm this default doesn't cause a regression the other direction (a genuinely new, high need
never surfacing) with a dedicated unit test in Phase 1's test list below.

**Seed the baseline on Full mode.** `DecideTurnModeAsync` (~297-303) resets `TurnsSinceReseed`
etc. on Full; add a pass after `RefreshInvolvedEntitiesAsync` populates `result.Npcs` /
`result.Scenes[].PresentNPCs` (Full mode only) that writes every NPC's full `KnownNeeds` into
`ctx.Cursor.SurfacedNeedValuesByEntityId[npc.Id]`, so Delta-mode drift is always measured from
what the client actually received, not from an empty/missing baseline. Exact insertion point:
locate the Full-mode branch of `Finalize` or wherever `result.Npcs`/`Scenes` are fully populated
and mode is confirmed `Full` — do this scan there, once per Full response, in Phase 1's own
work (do not guess the line number in this document; find it live when implementing, since
`RefreshInvolvedEntitiesAsync` is mode-agnostic and Full-only seeding must not run there).

**Phase 1 test list** (add to whatever the existing `MutationTools`/`take_turn` delta test
fixture is — locate it via `find_referencing_symbols` on `ChangedNeedsKeys` or `ApplyDeltaTrim`
before writing, don't create a new fixture file if one already covers this trim family):
- Three consecutive Delta-mode `take_turn` calls, each with a `NeedChange` of 1.0 (under the
  2.0 threshold individually) to the same need → the 3rd call's `KnownNeeds` includes that need
  (cumulative drift 3.0 ≥ 2.0), and the baseline resets to the surfaced value afterward.
- Same setup but a 4th call with no `NeedChange` at all for that need → need is NOT resurfaced
  again (baseline already caught up), confirming no double-count.
- A brand-new need key introduced mid-campaign via a single `NeedChange` of exactly the
  threshold value → surfaces on that turn (guards the "new key defaults to no-drift" logic
  above from over-suppressing).
- Full-mode reseed after several unsurfaced sub-threshold Delta drifts → confirms the baseline
  reset on Full matches live values exactly (no stale cumulative drift leaking across a reseed
  boundary).

**Done when:** all four tests pass, full existing suite stays green, and
`NeedsChangeSignificanceThreshold`'s doc comment in `CampaignConfig.cs` (~398-400) is updated to
mention it now gates cumulative drift, not just single-event delta.

## Phase 2 — Shrink unchanged `PresentNPCs` entries within a refetched scene

Closes gap 2. Depends on Phase 1's cursor-dictionary pattern but is otherwise independent code.

**Current shape:** once a scene passes the `AffectsLocationDetail`/`AffectsScenePresence` gate
and gets refetched, `summary.PresentNPCs = summary.PresentNPCs.Select(npc =>
ApplyDeltaTrim(ctx, npc)).ToList()` (`MutationTools.cs` ~1493-1495) field-trims every present
NPC but includes all of them at full (trimmed) shape regardless of whether that specific NPC's
presence or fields actually changed this turn.

**Add a per-scene "already fully surfaced, still true" cursor entry.** Mirror the existing
`SurfacedCompressedMemoryTopicsByEntityId` pattern: a
`Dictionary<string, List<string>> SurfacedPresentNpcIdsByLocationId` on `TurnCursor` recording,
per location, which NPC IDs were already sent as present as of the last time that scene was
included. On a refetch:
- An NPC ID present in both the cursor's recorded set and the live `PresentNPCs` set, with
  `ApplyDeltaTrim` gating everything to null (i.e. `ShouldSkipBehavioralSummary` /
  `ShouldStripUnchangedAppearance` / `ShouldStripUnchangedGear` all true, and no need drift from
  Phase 1) → replace the full trimmed entry with a minimal stub carrying only
  `Id`/`Name`/`IsPc`/`IsPartyCompanion`/`KeepAlive` (the fields `TurnResult.KnownCharacterIds`
  and the do-not-hallucinate check actually need) plus nulls everywhere else — **do not omit the
  entry** (hard constraint above).
- An NPC ID in the live set but NOT in the cursor's recorded set (newly arrived) → full trimmed
  entry as today, and add it to the cursor set.
- An NPC ID in the cursor's recorded set but NOT in the live set (departed/evicted) → drop from
  the cursor set; no wire representation needed (scene fetch already reflects them leaving).

Since `NpcPresenceSummary` is a `record` with a parameterless constructor already defined
(`V4Views.cs:331`, `this(null!, null!, null!, null!, null!, null!)`), the stub can be built with
a `with` expression off the existing trimmed record rather than a new type — keeps this in the
same shape `ApplyDeltaTrim` already returns, avoids a second DTO for callers to branch on.

**Open question to resolve before writing code, not guessed here:** whether "unchanged" for
stub purposes should be exactly "all of `ApplyDeltaTrim`'s existing per-field gates say
strip/skip" (cheap, reuses Phase-current logic, no new gate) or a dedicated
`AffectsScenePresence`-style check restricted to this one NPC's own WorldChanges. Recommend the
former — it's already computed by the time `ApplyDeltaTrim` returns, so detecting "everything
was stripped" is a single follow-up check on the already-built object, not new state.

**Phase 2 test list:**
- Scene with 3 present NPCs; only 1 has an `AppliedChange` this turn → response's
  `PresentNPCs` still has 3 entries (ids all present, satisfying `KnownCharacterIds`), but 2 are
  stub-shaped (verify via a helper asserting non-null-field-count) and 1 is fully populated.
- NPC leaves cursor's recorded set (evicted) then a different NPC with the same freed slot walks
  in later → newly-arrived NPC gets a full entry, not mistaken for "already surfaced."
- Full-mode reseed clears/repopulates `SurfacedPresentNpcIdsByLocationId` correctly (no stale
  scene-NPC pairs surviving a full resync where the scene's roster actually changed).

**Done when:** those tests pass, full suite green, and `KnownCharacterIds`'s existing tests (if
any — locate before starting) still pass unmodified, confirming the invariant this phase must
not break.

## Explicit non-goals (do not implement under this plan)

- Engine-generated narrative flavor text ("cheeks blush", "skittish") for any delta — stays the
  narration skill's job.
- Dropping an NPC entirely from `PresentNPCs` to save bytes — breaks `KnownCharacterIds`.
- A "turns unchanged" counter/array per NPC — superseded by the last-surfaced-value baseline
  cache in Phase 1/2, which needs no counting, just a stored value to diff against.
- Touching `BehavioralTension` or `ActiveInitiatives` gating — these are explicitly documented
  in `ApplyDeltaTrim` as "current state, not AppliedChanges, so never gated here" by original
  design; changing that is a separate decision, out of scope here.
